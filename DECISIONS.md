Why: `AgentRuntime.instantiate` sends `configure` when the SqlHost has a `value_limit`, and src/board_wasm.rs knew only `board`, so `Board.open({ module })` with `dist/nanocode_board.wasm` on such a host threw `unknown variant configure, expected board`. The board-only `Command::Configure` takes the same fields, so a value that the full module rejects is rejected the same way. test/board-module.test.ts opens a board with the board-only module on `Sql.open(path, { valueLimit })`, then posts and reads a task. Against build-3274348 it fails with that error. With the fixed module it passes, and test/board.test.ts passes 14 of 14 on the full module, on the board module, and on the board module with a 1 MiB `valueLimit` (0 of 14 before). Built against nanocode 9876777cf on Linux x86_64 with Rust 1.97.1, binaryen 133 and clang 22: `dist/nanocode_board.wasm` is 4,218,193 bytes. - feat(python): python3 sends scripts that import polars to a host-supplied second interpreter, `Python.Options.sci` (2026-11-17, sci lane). Why: polars 1.33.1 makes python.wasm about 64 MB (scripts/polars.mjs; the polars and split entries below), which can't sit beside the agent in a Cloudflare Worker's 64 MiB bundle, so `import polars` failed for every demo user. What: before compiling python.wasm, python3 scans the source it will run (`-c`, the script file, stdin, or `-m`'s module file) for an `import`/`from` of a module in `sci.modules` (`['polars']` by default; also `__import__` and `importlib.import_module` with a literal name; the scan is `importing` in commands/python.ts). A script that reaches polars through a module of its own runs on python.wasm first, and when it ends with an uncaught `ModuleNotFoundError` for one of those modules (or nanocode reports one missing), what it wrote is rolled back (the journal on a sync filesystem; the layered cache is simply not applied on an async one) and it runs again on the sci interpreter. `sci` is either `{ module, data }`, the polars python.wasm and python.data run in-process on the same files (Node, Vercel: `PythonSci.local()` reads them from the optional `nanocode-ts-polars` package), or `{ run(request, signal) }`, a runner elsewhere (`PythonSci.remote(binding)`). A remote run is sent argv, cwd, env (with PWD), stdin, maxMemoryBytes, timeoutMs and the files it may read: the files named on the command line, absolute paths quoted in the code or in the named scripts, then everything under the working directory and pip's site-packages, skipping `.git` and `node_modules`, up to `sci.sendBytes` (maxMemoryBytes by default, since the run can't hold more); files past that are named in a stderr line. The runner answers stdout, stderr, status and the files it created, changed or deleted, which python3 applies to the workspace, so charts appear in chat as before. `PythonSci.serve(request, { module, data })` is the other end (a fresh MemoryFileSystem and Bash per request, so commands the script starts run in that Worker's shell over the files it was sent), `PythonSci.assets(env.ASSETS)` joins python.data's two static assets, and both bodies are a little-endian u32 header length, a JSON header, then the files back to back (the format examples/python-sci already used). The Cloudflare app takes `workspace.pythonSci(env)` (a service binding or any sci runner); the Vercel harness takes `workspace.python` (python3's options, so `{ sci: PythonSci.local() }`). Without sci the default path is unchanged, and a script stopped at `import polars` prints, after its traceback, that polars runs on the separate polars interpreter this host doesn't offer. Limits: a rerun after the fallback repeats the commands the first run started; a remote run doesn't see files outside what it was sent (a path built at runtime outside cwd), and its children don't reach the main shell's commands. Checked: `node bench/python/sci.ts` 9/9 (scan cases; no sci; routed with a stand-in runner, argv, cwd, files sent, written and deleted files applied; a script file on an async filesystem; an unrouted script; the fallback through a helper module, sync and async, dropping what the first run wrote; in-process and `remote` to `serve` round trips with the default python.wasm and json as the routed module); `bench/python/subprocess.ts` 44/44; `bench/python/asyncfs.ts` 20/20; `CAPI=... bench/python/score.ts` packages 9/18, numpy 14/14, pandas 12/12, matplotlib 6/6, limits 4/4; `npm run check:types`; `npm run build:ts`.

This repository is nanocode-ts (nanocodexyz/nanocode-ts, formerly nanocode-wasm): the nanocode Rust SDK compiled into one WebAssembly module, the TypeScript host that runs it in any JavaScript runtime that can instantiate WebAssembly, such as Cloudflare Workers, Node, Deno and browsers, and TypeScript adapters for Vercel and Cloudflare, so a host repository writes only TypeScript and builds no Rust. Its sibling `../nanocodex` supplies the SDK; `sdk-revision.json` records the SDK master revision this package builds against; check out that revision in the sibling when preparing a fresh workspace. `.github/workflows/release.yml` builds every push to main against the SDK at `sdk-revision.json`, checked out beside it as `nanocodex/`, with the Rust release `rust-toolchain.toml` pins, checks it, packs it and publishes the tarball as the GitHub release `build-<short commit>`. Before that it publishes the WASM build outputs, `dist/nanocode_wasm.wasm`, `dist/interpreter.wasm`, `dist/models.js` and `dist/models.d.ts` with their digests in `dist/nanocode-wasm.json`, as the asset `nanocode-wasm-<fingerprint>.tgz` of the release `wasm-<fingerprint>` (`node scripts/publish-wasm.mjs --upload`), and checks out the SDK and runs Cargo only when that release does not exist yet. `node scripts/wasm.mjs` prints the fingerprint: the first 20 hex digits of a SHA-256 over `sdk-revision.json`, `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml`, `scripts/build.mjs`, `scripts/wasm.mjs`, the JavaScript files under `src/wasm`, every `src` Rust file and the interpreter's `Cargo.toml`, `Cargo.lock` and Rust files, so a push that changes only TypeScript reuses the last WASM release. `node scripts/publish-wasm.mjs` without `--upload` writes the asset to `output/`, from `dist/` when its manifest names the current fingerprint, or from a directory or a `build-<commit>` tarball given as its argument, which must come from a commit with the same Rust inputs; only builds against the SDK at `sdk-revision.json` may be uploaded, since the fingerprint does not cover `../nanocodex`. Hosts install the tarball, `"nanocode-ts": "https://github.com/nanocodexyz/nanocode-ts/releases/download/build-<short commit>/nanocode-ts-<short commit>.tgz"`, which their lockfile pins with its integrity: nanocodexyz/durable-cloudflare (formerly nanocode-worker) and nanocodexyz/durable-vercel; nanocodexyz/nanocode-site builds the package from a checkout instead. `dist/` is build output, ignored by Git and listed in `package.json`'s `files`, so the tarball carries the compiled JavaScript, declarations and module and installing it needs neither Rust nor a TypeScript build. To consume a change without waiting for its release, a host pins the commit, `"nanocode-ts": "github:nanocodexyz/nanocode-ts#<commit>"` (`npm install github:nanocodexyz/nanocode-ts#<commit>`, which also updates the lockfile; editing only `package.json` leaves an installed git dependency in place). npm clones the commit, installs its devDependencies and runs `prepare`, `scripts/prepare.mjs`: it keeps `dist/`'s WASM outputs when `dist/nanocode-wasm.json` names the commit's fingerprint and their digests match, else downloads `wasm-<fingerprint>` over HTTPS without authentication (`NANOCODE_TS_WASM_URL` replaces the URL with another URL, a `file:` URL or a path), checks its manifest and copies it into `dist/`, and when no such release exists builds the WASM with `scripts/build.mjs` if Cargo and `../nanocodex` are present, or fails naming the fingerprint. It then runs `npm run build:ts` (both `tsc` builds and `scripts/zyzz.mjs`) unless `output/typescript-build-fingerprint` matches the TypeScript inputs, so npm's second `prepare` while packing the clone is free. Installing a commit that changes only TypeScript takes about 20 seconds; a commit that changes Rust inputs installs once its push to main has published `wasm-<fingerprint>`, and every later TypeScript-only commit at once. `npm install /path/to/nanocode-ts`, its `--install-links` form and `npm pack` run the same `prepare`, as does `npm install` in a checkout. pnpm runs a git dependency's `prepare` only when the host's `pnpm-workspace.yaml` lists it under `allowBuilds` (`nanocode-ts@<resolved spec>: true`). Commits before the releases kept `dist/` in Git, so their `github:nanocodexyz/nanocode-ts#<commit>` pins still install. Generic agent, durability, turn and event logic belongs in the SDK, host-agnostic bridge glue in `src/*.ts`, a platform's runtime and wiring in its adapter under `src/<platform>/` (the whole Durable Object runtime in `src/cloudflare/`, the durable-harness app in `src/vercel/`, each with a browser `transport.ts`), so a host repository only configures and skins it, the store and React chat the hosts share in `src/client/` and `src/react/`, and an application's own choices (its tools, models, authorization policy, pages and commands) in the host repository.

Do not add Cargo features or wasm-bindgen glue. The host-agnostic sources use no platform types or bindings: no `DurableObjectState`, no `@cloudflare/workers-types`, no Node APIs; `tsconfig.json` checks `src/*.ts`, `src/cloudflare/Sql.ts` and both `transport.ts` files against the standard web platform types only, `tsconfig.vercel.json` checks `src/vercel/*.ts` against Node's, and `tsconfig.cloudflare.json` checks `src/cloudflare/*.ts` against `@cloudflare/workers-types` (the runtime imports `DurableObject` from `cloudflare:workers` and the module as `nanocode-ts/nanocode_wasm.wasm`, which the package resolves to itself); `tsconfig.cloudflare.build.json` emits that directory, which `tsconfig.build.json` leaves out. `package.json` marks only `*.css` as side effects, and every runtime is its own subpath, so a page that imports `nanocode-ts/cloudflare/transport` or `nanocode-ts/vercel/transport` bundles none of the Worker, Node or WebAssembly code. Hosts supply everything platform-specific through the interfaces below or take an adapter's. The Rust side is single-threaded and keeps its state in `thread_local` cells, with no `Mutex` or `RwLock`. TypeScript uses only erasable syntax (`erasableSyntaxOnly`, `verbatimModuleSyntax`) and imports with `.ts` extensions, so Node 22.18 or newer runs the sources directly with type stripping from a checkout or a `file:` link, and bundlers such as esbuild and Wrangler compile them.
